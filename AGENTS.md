# Правила для агентов

## Новый сервис (автоматизация)

Доступ к сервисам выдаётся каждому сотруднику отдельно (`platform.user_service_access`),
поэтому новый сервис нельзя «просто добавить»: без шагов ниже он окажется открыт всем
или не откроется никому.

1. Бэкенд: запись в `backend/modules/platform/domain/services.py` (`id`, `title`) —
   источник правды для диалога доступов в админке.
2. Бэкенд: роутер подключается в `backend/app/api/router.py` через `include_service(router, "<id>")`,
   и на него встаёт `require_service`. Напрямую `router.include_router` не вызывается.
   Роутеры без неё (вход, `/admin/*`, `/onec`, extension) идут через `include_open` и
   названы по тегам в `OPEN_ROUTER_TAGS` теста `backend/tests/platform/test_service_access.py`.
3. Фронт: запись в `frontend/src/features/automations/nav.ts` (тот же `id`, название,
   иконка) и страница в `App.tsx` внутри `ServiceRoute`.
4. После выкатки сервис виден только администраторам, пока доступ не выдан в админке.
   Миграция и backfill не нужны. `id` стабильный: переименовывать можно только `title`.

Эти правила держат три теста, они упадут, если шаг забыт:

- id в каталоге бэкенда совпадают с `nav.ts`;
- каждый роутер подключён через `include_service` или `include_open`, открытые перечислены явно, у каждого сервиса каталога есть роутер;
- пользователь без доступа получает `403` на каждом сервисе каталога, с доступом — нет.

В тестах рабочих маршрутов токен берётся через `backend/tests/operators.py::operator_token`:
токен со случайным uuid больше не проходит, пользователь должен существовать в базе.
