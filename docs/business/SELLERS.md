# Селлеры и автоматизации

Правило, из-за которого пришлось переделывать: селлер существует **сам по себе**, а не внутри
автоматизации.

## Реестр и членство — разные вещи

- `wb_core.sellers` — реестр. Только здесь селлера заводят, правят и убирают.
- Участие в автоматизации — отдельная таблица **внутри модуля** автоматизации
  (`wb_reviews.tracked_sellers`). Своя таблица, потому что у подключения бывают собственные
  настройки, а модуль обязан оставаться автономным.
- До этого членства не существовало: прогон брал всех селлеров из реестра подряд, и «убрать из
  автоматизации» было нечем — кнопка удаляла селлера из базы вместе с историей отзывов.

## Три разных действия, которые раньше были одним

| Действие | Что происходит | Обратимо |
| --- | --- | --- |
| Отключить от автоматизации | сбор прекращается, собранное остаётся | да, подключить заново |
| Архивировать | уходит из всех автоматизаций, ключ удаляется, история остаётся | да, через восстановление |
| Удалить навсегда (`?purge=true`) | каждая автоматизация стирает своё, потом исчезает селлер | нет |

Архивация удаляет строку с ключом не ради экономии: `key_fingerprint` уникален, и оставшийся ключ
архивного селлера не дал бы завести того же селлера заново — API отвечал бы «ключ уже
используется» без объяснения, какой именно.

## Кто чистит чужие таблицы

Никто. `wb_core` не знает про схемы автоматизаций — раньше знал, через сырой
`DELETE FROM wb_reviews.daily_review_counts` внутри репозитория, и каждый новый модуль пришлось бы
дописывать в этот запрос руками.

Вместо этого модуль реализует `AutomationEnrollment` (`seller_ids` / `attach` / `detach` / `purge`)
и регистрируется в DI-провайдере одной строкой. Реестр спрашивает через порт.

`purge` стирает историю, но **не трогает завершённые прогоны**: `sync_run_sellers` — это запись о
том, что автоматизация делала той ночью, и API уже показывает job удалённого селлера как
«Удалённый селлер».

## Что это значит для расписания

Прогон покрывает **подключённых** селлеров, а не всех. Пересечение с активными считается заново
на каждом прогоне: архивный селлер отцепляется при архивации, но оставшаяся строка членства не
должна отправить job на селлера, чьего ключа у нас больше нет.
