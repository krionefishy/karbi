# Как мы читаем Wildberries

## Какие API используем

| Группа | Что берём | Кто |
| --- | --- | --- |
| Контент | каталог карточек, архивные карточки, размеры и баркоды | каталог-синк |
| Отзывы | отзывы селлера тремя проходами | автоматизация отзывов |
| Статистика | остатки FBO, заказы | автоматизация оборачиваемости |
| Маркетплейс | остатки FBS по складам продавца | автоматизация оборачиваемости |

Только чтение. Ничего не публикуем и не меняем на стороне WB.

## Лимиты

WB считает бюджет **token bucket на пару «категория API + токен»** — не на аккаунт и не на
наш IP:

- `X-Ratelimit-Limit` — это **не квота запросов, а ёмкость всплеска** (burst).
- `X-Ratelimit-Reset` — за сколько секунд ведро наполнится доверху, то есть один токен
  возвращается каждые `reset / limit` секунд.
- `X-Ratelimit-Remaining` — сколько запросов можно отправить прямо сейчас без пауз.
- `X-Ratelimit-Retry` (в ответе 429) — через сколько секунд можно повторить.

**Ответ 4XX списывается как десять запросов.** Поэтому 429 нельзя «переждать повторами»:
каждая попытка углубляет яму. Замер на проде показал, как это выглядит — ведро
восстанавливалось 402 секунды после серии повторов. Задача троттла не в том, чтобы
корректно обработать 429, а в том, чтобы никогда его не получить.

**Ёмкость зависит от типа токена.** Замер: персональный токен — burst 6 при reset 2 с
(около трёх запросов в секунду), базовый — burst 1. Разница шестикратная, поэтому
константа в конфиге негодна: она либо втрое тормозит хороший токен, либо не спасает
слабый.

## Троттлинг

```mermaid
flowchart LR
    call["Запрос к WB"]
    bucket[("Вёдра в Redis<br/>ключ + хост")]
    wb{{"WB"}}
    headers["Заголовки X-Ratelimit-*"]

    call -->|"занять место"| bucket
    call --> wb
    wb --> headers
    headers -->|"пересчитать паузу"| bucket
```

- Бюджеты из конфига — грубая страховка **до первого ответа**; дальше клиент живёт по
  заголовкам и держит паузу `reset / limit`, когда всплеск заканчивается.
- Вёдра лежат в Redis и общие для всех воркеров: два процесса с одним ключом селлера не
  должны тратить бюджет вслепую друг от друга.
- Если Redis недоступен, троттл переходит на локальное окно и не роняет синхронизацию.
- Если WB просит ждать дольше предельного ожидания, клиент падает временной ошибкой, и
  задача уезжает в отложенный повтор. Занимать воркер на минуты бессмысленно: токен с
  такой ёмкостью полное сканирование всё равно не закончит — его нужно менять на
  персональный.

## Ошибки

Ошибки делятся на два вида, и это деление определяет поведение всей платформы:

| Вид | Примеры | Что делаем |
| --- | --- | --- |
| Временная | 429, 5xx, сеть, таймаут | повтор с backoff, задача возвращается в очередь |
| Постоянная | 401/403 (ключ отозван), 400 | повторять нечего, фиксируем ошибку у селлера |

Отдельно живёт случай «данных нет»: у селлера может не быть архивных карточек или
доступа к части методов. Это не ошибка синхронизации, но и не повод считать, что артикулов
не существует, — см. [business/ARTICLE_LIFECYCLE.md](../business/ARTICLE_LIFECYCLE.md).
