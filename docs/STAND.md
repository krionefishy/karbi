# Локальный стенд «Контроль скриншотов ДБС»

Стенд поднимает на Mac всё, что нужно модулю, чтобы его можно было прокликать руками: кабинет менеджера,
админку, расширение Chrome и весь конвейер (outbox → Kafka → воркер → вердикт, файлы в S3). Ни WB, ни
релея, ни Telegram он не трогает. Распознавание по умолчанию — поддельная модель, без ключа и без сети.

## Запуск

Нужны `colima`, `docker` (CLI с compose), `just`, `uv` и `node` (только для сборки расширения на хосте).

```sh
just stand-up      # поднять (первый раз ~5 минут на сборку образов, потом ~1,5 минуты)
just stand-down    # остановить контейнеры, данные сохраняются
just stand-reset   # стереть базу, Kafka и S3 и поднять заново; логины те же
just stand-logs wb-screenshot-control-worker fake-vlm   # логи
```

`stand-up` сам создаёт профиль Colima `karbi-stand` (2 CPU, 5 ГБ, диск 30 ГБ) и работает только
через его docker-контекст `colima-karbi-stand`. Профиль `default` и его контейнеры не трогаются; после
`colima start` прежний текущий контекст возвращается на место. Остановить ВМ целиком:
`colima stop karbi-stand`. Размер ВМ задают `STAND_CPU`, `STAND_MEMORY_GB`, `STAND_DISK_GB`.

При первом запуске создаются два файла (оба в `.gitignore`):

- `deploy/stand/.env.stand` — случайные локальные секреты: пароли базы и Redis, JWT, ключи S3, ключ HMAC
  скриншотов. Режим `SCREENSHOT_CONTROL_MODE=shadow`.
- `deploy/stand/.credentials.txt` — логины стенда, строки `роль логин пароль`: администратор
  `stand-admin` и менеджеры `manager-anna`, `manager-boris`. Пароли случайные, смотрите их в файле.
  Начальные данные заливает `deploy/stand/seed.py`; он идемпотентен: можно поменять пароль в файле и
  выполнить `deploy/stand/stand.sh seed`.

В этой ветке доступа к сервисам по сотрудникам ещё нет: «Контроль скриншотов ДБС» открыт любому
вошедшему, админка — сотруднику с флагом администратора. Выдавать доступ не нужно.

## Адреса

| Что | Адрес |
| --- | --- |
| Кабинет менеджера | http://localhost:8090/automations/wb-screenshot-control |
| Админка | http://admin.localhost:8090/admin/screenshots |
| API | http://localhost:8090/api/v1 (напрямую — http://localhost:8091, схема — http://localhost:8091/docs) |
| S3-консоль (RustFS) | http://localhost:19001, логин и пароль — `STAND_S3_ACCESS_KEY` / `STAND_S3_SECRET_KEY` из `.env.stand` |
| PostgreSQL | 127.0.0.1:55440, база и пользователь `karbi`, пароль — `DB_PASSWORD` из `.env.stand` |

Админка открывается по имени хоста `admin.` (`frontend/src/features/admin/entry.ts`). Chrome резолвит
любое `*.localhost` в 127.0.0.1, поэтому `admin.localhost` работает без правки `/etc/hosts`; nginx стенда
(`deploy/stand/nginx.conf`) отдаёт фронт и `/api` на обоих именах. Войти в админку надо отдельно: сессия
привязана к имени хоста. Safari и curl старых версий `*.localhost` могут не знать — откройте в Chrome.

S3 вместо Cloud.ru — RustFS (образы MinIO из Docker Hub и quay.io больше не раздаются, RustFS совместим по
API). Бакет `karbi-stand` создаётся сам. Presigned-ссылки подписаны на `http://s3.localhost:19000`: внутри
докера это сервис `s3`, снаружи — проброшенный порт, поэтому миниатюры открываются прямо в браузере.

## Тестовые скриншоты

`just stand-up` кладёт в `deploy/stand/samples/` набор синтетических скринов (в репозитории только
генератор `deploy/stand/make_samples.py`, сами картинки — нет). Даты на скринах относительные
(«вчера и раньше»), поэтому набор пересобирается раз в день; вручную — `just stand-samples`, ещё N
уникальных — `just stand-samples --random 10`. Что с каким файлом должно получиться, если грузить в
таком порядке:

| Файл | Кто | Ожидаемо |
| --- | --- | --- |
| 01-desktop-unique.png | менеджер 1, «полож» | Принят, плашка KPI +1 |
| 04-same-file-as-01.png | он же | Дубль (тот же файл) |
| 05-recoded-copy-of-01.jpg | он же | Дубль (другой файл, тот же кейс) |
| 02, 03, 10–14 | кто угодно | Принят (03, 11, 14 — чат в телефоне) |
| 01-desktop-unique.png | менеджер 2 | Дубль, в админке — «Подозрения», другой менеджер |
| 06-other-chat-same-text.png | менеджер 2 | Проверяется: тот же текст и время, другой chatId |
| 07-desktop-no-outcome.png | без исхода | «Нужен исход»; исход позже — решение, через сутки без исхода — отказ |
| 08-recognition-error.png | любой | Модель отвечает 500: 4 попытки (≈6,5 мин), затем «Проверяется» |
| 09-looks-edited.png | любой | Проверяется: похоже на правку картинки |

Важно про 08: пока более ранний скрин в работе, решения по более поздним ждут его (до 30 минут, так
устроен конвейер). Поэтому в эти 6,5 минуты остальные загрузки висят «В обработке» — это не поломка
стенда.

Генератор и фейк рисуют и «читают» одни и те же поля: в левом нижнем углу каждого скрина — полоска из
квадратов, по ней фейк узнаёт образец (и перекодированную копию тоже). Окно браузера нарочно не во весь
экран и на цветных обоях: одинаковые окна разных чатов почти совпадают по dHash всего кадра (9×8), и
система честно отправляет их на проверку как «похожую картинку с другими полями».

## Поддельная модель и сценарии

`deploy/stand/fake_vlm.py` — OpenAI-совместимый `/v1/chat/completions`, контейнер `fake-vlm`. Отвечает
строгим JSON по схеме `ScreenshotAnswerV1` / `AddressBarAnswerV1`
(`backend/modules/wb_screenshot_control/domain/prompt.py`). Поля детерминированы: у образцов стенда — по
метке, у любой другой картинки — по sha256 присланных байтов (одна картинка → те же chatId, время, текст;
разные → разные). Вырезку адресной строки фейк сопоставляет с кадром, из которого она вырезана.

Поведение меняется без перезапуска: скопируйте `deploy/stand/scenarios.example.json` в
`deploy/stand/scenarios.json` (файл в `.gitignore`) и правьте. Правило — `match` и действие:

- `match`: `sample` (имя из `samples/manifest.json`), `request` (номер запроса к фейку с его старта),
  `kind` (`frame` | `address_bar`), `sha256` (картинки, как в логе `just stand-logs fake-vlm`);
- действие: `error` (HTTP-статус числом, `"timeout"`, `"invalid_json"`, `"empty"`), `answer` (ответ
  целиком) или `patch` (слияние с выведенным ответом, например `{"quality": {"photo_of_screen": true}}`
  или `{"chat_id": {"value": null}}`); `times` — сколько раз сработать.

Пример из `scenarios.example.json`: 12 — две ошибки 503 и успех с третьей попытки; 13 — адресная строка
прочитана иначе, чем кадр (проверка, `extraction_disagreement_chat_id`); 14 — «фото экрана» (отказ).

## Настоящая модель Cloud.ru

В `deploy/stand/.env.stand` раскомментируйте и заполните две строки и перезапустите `just stand-up`:

```sh
LLM_BASE_URL=https://foundation-models.api.cloud.ru/v1
FOUNDATION_MODELS_API_KEY=<ключ>
```

Модель — по умолчанию из `config.docker.yaml` (`Qwen/Qwen3.6-35B-A3B`, ремонтный запрос —
`Qwen/Qwen3.5-397B-A17B`). Назад к фейку — закомментировать строки и снова `just stand-up`. Метка
синтетических скринов настоящей модели не нужна: она читает нарисованный текст. Учтите, что каждый
скрин стоит денег и что ретраи у недоступной модели занимают до 6,5 минут.

## Расширение Chrome

Стендовая сборка отличается от боевой двумя вещами: адрес сервиса по умолчанию `http://localhost:8090`
и в `optional_host_permissions` добавлены `http://localhost/*` и `http://127.0.0.1/*` (без них Chrome не
даст доступ к http-адресу при сопряжении). Боевой `extension/screens/manifest.json` не меняется: правится
копия в каталоге сборки (`deploy/stand/build-extension.sh`).

1. `just stand-extension` → `deploy/stand/extension/unpacked/` (или скачайте архив со страницы
   «Подключения» — http://localhost:8090/extension/marketplace-auto-screenshots.zip — и распакуйте).
2. Chrome → `chrome://extensions` → «Режим разработчика» → «Загрузить распакованное» → папка `unpacked`.
3. В кабинете менеджера: «Контроль скриншотов ДБС» → вкладка «Подключения» → получить код.
4. Расширение → «Параметры»: адрес уже `http://localhost:8090`, введите код, «Подключить», разрешите
   доступ к localhost.
5. Снимок делается только на вкладке `https://seller.wildberries.ru/chat-with-clients…` (Alt+Shift+S,
   исход выбирается в попапе). Скрин настоящего кабинета фейк прочитает по sha256 — поля будут
   выдуманными, но стабильными; chatId берётся из адреса вкладки.

## Память

Под нагрузкой контейнеры стенда держат около 0,9 ГБ (Kafka ~250 МБ, воркер ~200 МБ, API ~160 МБ, S3
~130 МБ), ВМ с кешем — около 1,4 ГБ из 5. Если 5 ГБ много, `STAND_MEMORY_GB=3` перед первым
`just stand-up` (для уже созданного профиля — `colima stop karbi-stand` и `colima start karbi-stand --memory 3`).
