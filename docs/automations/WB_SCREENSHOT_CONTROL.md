# Контроль скриншотов ДБС

Статус: приём, конвейер (распознавание и решение), хранилище, API менеджера, расширения и
админа, страницы и расширение Chrome готовы и покрыты тестами на PostgreSQL и Redis, включая
сквозной тест через настоящие `Extractor` и `decide` и набор «красной команды». S3 в тестах —
фейк, модель — заготовленные ответы. На живом S3, живой модели и живом Kafka не проверялось;
пороги дедупа не откалиброваны на реальных скринах (см. «Оценка»). Telegram — второй релиз.

## Зачем

Менеджеры, которые разбирают плохие отзывы WB, подтверждают результат скриншотом с подписью
одного из трёх исходов: «полож» (отзыв положительный), «доп» (договорились, отзыв изменён на
положительный), «удален» (отзыв удалён). На принятых скриншотах держится KPI менеджера,
поэтому нужна защита от повторов и подделок, а спорное должен видеть администратор.

Единица работы — скриншот с подписью: жизненного цикла кейса нет, подпись против содержимого
не сверяется. Сверки с WB тоже нет; задел под неё — нормализованные `chat_id`, время и артикул
отдельными колонками `submissions`.

Технические имена: модуль `wb_screenshot_control`, id автоматизации `wb-screenshot-control`,
схема `wb_screenshot_control` (ревизии `sc…`), воркер `wb-screenshot-control-worker`. В
каталоге это инструмент (`kind="tool"`): селлеров не подключают.

## Каналы

| Канал | Вход | Авторизация |
| --- | --- | --- |
| Веб | `POST /api/v1/wb/screenshot-control/submissions`, multipart; исход можно выбрать позже | JWT сотрудника |
| Расширение Chrome | `…/extension/*`, снимок видимой вкладки, URL вкладки из `tab.url`; исход обязателен | токен установки `mas_…`, выдаётся по коду сопряжения из 8 символов; обмен кода под жёстким лимитом на IP |
| Telegram | второй релиз | флаг `telegram_enabled=false`; таблицы привязки уже есть |

Админ-панель — `/api/v1/admin/screenshot-control/*`, только `CurrentAdmin`, на рабочем
домене префикс закрыт nginx. Контракт целиком — `presentation/http/schemas.py`, JSON-схема —
`just openapi --tag wb-screenshot-control`. Машинный код ошибки — заголовок `X-Error-Code`
(новая для проекта конвенция), текст — как везде, в `detail`.

## Конвейер

Transactional outbox и два консьюмера вместо очереди-таблицы: приём одной транзакцией пишет
`files`, `submissions` (`stage=processing`) и события `screenshot.submitted` и
`storage.s3.wb-screenshot-control.upload`; распознавание пишет `extractions` и
`screenshot.extracted`; решение идёт по одному в порядке приёма — все `extracted` одним ключом
партиции — и пишет вердикт, журнал `verdict_events` и `screenshot.verdict-ready`. Outbox и
inbox общие (`wb_core`), повторная доставка любого события ничего не портит.

| Топик | Что |
| --- | --- |
| `wb.screenshot-control.screenshot.submitted` | скрин принят, ждёт распознавания |
| `wb.screenshot-control.screenshot.extracted` | поля прочитаны, ждёт решения |
| `wb.screenshot-control.screenshot.verdict-ready` | вердикт готов |
| `storage.s3.wb-screenshot-control.upload` / `.delete` | запись и удаление в S3 |

- **Точная копия файла** (тот же sha256 у не отклонённого скрина с исходом) получает `duplicate`
  сразу при приёме, без модели.
- **Распознавание**: один запрос к модели по кадру целиком (длинная сторона до 2000 px) и, у окна
  браузера не из расширения, второй — по увеличенной вырезке адресной строки: это второе мнение о
  chatId. У расширения chatId берётся из адреса вкладки. Невалидный JSON — один ремонтный запрос
  запасной моделью. Сбой сервиса модели (сеть, таймаут, 429, 5xx) — повтор через 15 с, 60 с,
  5 мин; после `extraction_max_attempts` (4) неудач — `needs_review/extraction_failed`: сбой нашей
  стороны менеджера не штрафует. Распознавание живёт у файла: копия файла модель не зовёт.
- **Порядок решений**: решение по скрину ждёт (до 3 мин, перепроверка раз в 30 с) более ранний
  скрин с исходом, который ещё в работе, — иначе поздний занял бы место оригинала. Ожидание
  **глобальное**, но короткое: пока чей-то ранний скрин в повторах распознавания, решения других
  откладываются не дольше 3 минут; если оригинал задержался дольше, поздний решается как есть.
- **«Ядовитое» сообщение**: если обработчик падает на одном и том же сообщении (баг, нарушение
  ограничения БД) 5 раз подряд (паузы 1, 2, 5, 10 с), консьюмер пишет `screenshot_event_parked`
  уровнем ERROR, переводит скрин без вердикта в `needs_review/extraction_failed` (журнал: actor
  `system`, note «ошибка конвейера…»), коммитит оффсет и идёт дальше — иначе одно сообщение
  `extracted` (все они идут одним ключом) остановило бы решения по всем менеджерам. Уже решённый
  скрин не трогается. У событий хранилища так же, без смены вердикта: повтор сделает сверка.
- **Ожидание исхода**: скрин без исхода после распознавания **не решается**: `stage=extracted`,
  менеджер видит `awaiting_outcome`. Выбор исхода (`PATCH …/outcome`) публикует новое
  `screenshot.extracted`, и решение идёт обычным путём. Нет исхода через `outcome_ttl_hours`
  (24 ч) — фоновый шаг воркера (раз в минуту) ставит `rejected/no_outcome`; решённые скрины этот
  шаг не трогает. Пока исхода нет, скрин не оригинал ни для кого (скрин + подпись — единица
  работы): копия с исходом, присланная раньше подписи, станет оригиналом, а неподписанный — её
  дублем. На экране «Конвейер» ждущие исхода в очередь не входят, задержка «приём → вердикт»
  считается от выбора исхода.

Фоновые шаги воркера: истечение исхода — раз в минуту; сверка хранилища (зависшие выгрузки,
пропавшие объекты, сироты staging) — раз в час; чистка по сроку — раз в сутки в 04:10 МСК: файлы
в S3 (только с S3) и тексты в базе (всегда, см. «Хранение»).

При старте api и воркер пишут ERROR `screenshot_control_disabled`, если модуль выключен из-за
отсутствующего ключа HMAC, а воркер — WARNING `screenshot_control_model_key_missing`, если при
`mode≠off` не задан `FOUNDATION_MODELS_API_KEY`.

## Вердикты

| Вердикт | Что значит | В KPI |
| --- | --- | --- |
| `accepted` | засчитан | да |
| `duplicate` | повтор уже загруженного кейса | нет |
| `needs_review` | спорно, ждёт администратора | нет, пока не одобрен |
| `rejected` | не скриншот, не читается или нет исхода | нет |

Менеджер видит статус (`awaiting_outcome`, `processing` или вердикт) и узкий словарь причин:
дубль — «Этот скриншот уже загружен ранее» (чей — нет), проверка — «Принят, проверяется»,
отказ — что поправить (`no_outcome`, `not_wb_screenshot`, `cropped_missing_panel`,
`unreadable`). Пороги и детали эвристик не раскрываются. Полный словарь — `ReasonCode` в
контракте, у администратора. Порядок правил — таблица 8.2 архитектуры, код — `domain/decide.py`
и `domain/rules.py`; первая «жёсткая» причина задаёт вердикт, остальные копятся.

| Причина | Вердикт | Когда |
| --- | --- | --- |
| `no_outcome` | rejected | исход не выбран за `outcome_ttl_hours` |
| `exact_file` (+`cross_user_duplicate`) | duplicate | тот же файл уже у не отклонённого скрина |
| `not_wb_screenshot`, `unreadable`, `cropped_missing_panel` | rejected | не чат WB; кадр нечитаем или обрезан, и ключевые поля не прочитаны |
| `photo_of_screen` | rejected | фото экрана камерой или блики: принимаются только нативные скриншоты |
| `case_key` (+`cross_user_duplicate`, `caption_conflict`) | duplicate | тот же кейс: chatId + время до минуты + текст (S_text ≥ `text_dup`); у телефона — время и текст реплики с датой либо с совпавшим HMAC имени или артикулом |
| `messages_overlap` | duplicate | телефон: продолжение того же диалога, реплики покупателя пересекаются |
| `near_image` | duplicate | полей нет, а кадр почти тот же (dHash ≤ 6) |
| `caption_conflict` | needs_review | тот же менеджер прислал тот же кейс с другим исходом (возможно, исправляет) |
| `same_chat_same_text_other_time`, `same_chat_similar_text` | needs_review | тот же чат, тот же или почти тот же текст (S_text ≥ `text_maybe`), другое время — похоже на правку DOM. Держит кейс любой не отклонённый кандидат с исходом, в том числе ещё на проверке |
| `same_text_time_other_chat` (+`cross_user_duplicate`) | needs_review | тот же текст и минута, другой chatId — подмена адреса или chatId |
| `same_text_other_time` (+`cross_user_duplicate`) | needs_review, high | чат другой или не прочитан, текст тот же или почти тот же (S_text ≥ `text_maybe`, оба не короче 2 × `min_text_len` = 50 символов), время любое — подмена chatId вместе со сдвигом времени или заменой слов. У телефона — ещё и тот же текст реплики (≥ `text_dup`, ≥ `min_text_len`) в другое время |
| `possible_duplicate`, `weak_key` | needs_review | частичные совпадения; короткий текст без chatId |
| `near_image_conflict` | не влияет на вердикт | похожий кадр при противоречащих полях: запись для админа, пока хеш не откалиброван на реальных скринах |
| `extraction_failed` | needs_review | модель не ответила за все попытки |
| `extraction_disagreement_chat_id` / `_time` / `_text` | needs_review | два чтения разошлись (кадр и вырезка, текст и числа времени) |
| `chat_id_unreadable`, `url_not_chat` | needs_review | у окна нет chatId; вкладка расширения — не чат WB |
| `review_time_unreadable`, `review_date_implausible` | needs_review | время не прочитано; отзыв старше `review_age_max_days` (120) или в будущем |
| `possible_tampering` | needs_review | следы правки |
| `clock_skew`, `late_upload` | needs_review | часы расширения спешат больше чем на 15 мин; выгрузка из очереди старше 72 ч |
| `upload_burst` | needs_review | больше `burst_per_hour` (60) загрузок за час |
| `audit_sample` | accepted | случайная выборка `audit_percent` (4 %) принятых на аудит; KPI засчитан сразу |

## Уникальность

Три уровня (архитектура, раздел 7): точный файл (sha256), ключ кейса из распознанных полей и
похожесть кадра (dHash всего кадра — только подсказка). Ключ кейса окна браузера — chatId +
время отзыва до минуты + текст отзыва; телефона (chatId на экране нет) — последняя реплика
покупателя со временем, весь набор его реплик и слабые признаки (HMAC имени, артикул).
Тексты нормализуются (регистр, ё, пунктуация, эмодзи, пробелы, невидимые символы, хвост
«Показать полностью»), сравнение — S_text = 1 − расстояние Левенштейна / длина. Кандидаты ищутся
по индексам за `dedupe_window_days` (90 дней); отклонённые и неподписанные не в счёт.

Кандидатов подбирает `repository.candidates` — отдельный ограниченный запрос на каждый признак,
затем объединение по id (раньше был один `OR` с обрезкой 500 самых старых, и при шуме слабого
признака настоящий дубль отрезался):

| Признак | Лимит | Порядок |
| --- | --- | --- |
| тот же файл | 50 | самые ранние (корень цепочки) |
| `chat_id_norm` | 200 | свежие |
| `text_key` (минута + текст) | 100 | свежие |
| `text_minhash` (`&&`, GIN-индекс) | 200 | больше совпавших позиций, затем свежие |
| `key_time` ± 2 мин (± 1 день у телефона без даты) | 200 | ближайшие по времени |
| dHash кадра ≤ `near_dhash_soft` (12) | 100 | ближайшие по расстоянию |
| реплики телефона | 100 | свежие |

`text_minhash` — 8 MinHash по 3-словным шинглам `text_norm` (`domain.similarity.text_minhash`,
детерминированно, без зависимостей; номер позиции вшит в старшие биты, так что `&&` — совпадение
в одной позиции). Это ключ без чата и времени: замена слова в отзыве из 15 слов находится почти
наверняка, трёх слов — примерно в 98 % случаев (тест на случайных заменах). Ищется только у текстов
не короче `min_text_len`; меньше трёх слов — ключа нет. Колонка и индекс — миграция `sc003`, она же
заполняет старые строки. Функцию менять только вместе с новой миграцией пересчёта.

Сдвиг времени на цифру путаницы (06 ↔ 08, 3 ↔ 8 и т. п.) считается тем же временем: такую
правку нельзя отличить от ошибки чтения, и она уходит в дубль, а не в засчитанные.

### Что не ловится

Закреплено тестами `test_hole_*` в `backend/tests/wb_screenshot_control/test_red_team.py`
(XFAIL в отчёте pytest; закроют дыру — тест упадёт и напомнит обновить список). Остальные
попытки набора ловятся как дубль или проверка: подмена chatId — в том числе **вместе** со сдвигом
времени, заменой одного или трёх слов, другим днём и другим менеджером (`same_text_other_time`,
у другого менеджера ещё `cross_user_duplicate`); правка времени и слов в том же чате, в том числе
рядом с оригиналом, который ещё на проверке; регистр, эмодзи, невидимые символы, усечение, обрезка
и пересжатие кадра, фото экрана, повторы, перенос между менеджерами, всплеск загрузок. Красная
команда сравнивает с кандидатами в памяти; что SQL находит тех же кандидатов, проверяют
`test_repository.py` (каждый признак и шум из 520 строк) и сквозной тест «подмена chatId + время +
слово» на живой БД.

Ложные срабатывания, которые мы принимаем: длинный (≥ 50 символов) почти одинаковый текст у разных
покупателей в разных чатах уходит на проверку (`same_text_other_time`), а не засчитывается сразу;
короче — новый кейс. Одинаковый шаблон в ту же минуту в другом чате — тоже проверка
(`same_text_time_other_chat`).

- **правка DOM нового кейса** — выдуманный или чужой отзыв, присланный впервые: сравнивать не с
  чем, сверки с WB нет по решению заказчика;
- **чужой кейс первым** — засчитан тому, кто прислал раньше; настоящий автор получит дубль, пару
  с `cross_user_duplicate` админ увидит в очереди дублей, но вердикт первого не меняется;
- **подпись не того исхода** — по содержимому подпись не проверяется (решение заказчика);
- **текст переписан целиком** в том же чате с другим временем — для правил это другой отзыв
  того же покупателя;
- **часы расширения отстают** меньше чем на 72 ч — неотличимо от выгрузки из оффлайн-очереди
  (спешащие часы ловятся как `clock_skew`).

## Режимы

| `mode` | Приём | Конвейер | KPI |
| --- | --- | --- | --- |
| `off` | 503 `module_off` (кроме `GET /config`) | воркер не слушает топики | — |
| `shadow`/`enforce` без ключа HMAC | как `off`: 503 `module_off` с текстом «не задан ключ HMAC» | как `off` | — |
| `shadow` | работает | вердикты пишутся | `preliminary=true` в сводке, экспорте и `/managers` |
| `enforce` | работает | так же | боевой; дни раньше `kpi_from` — всё ещё `preliminary` |

Без `SCREENSHOT_CONTROL_HMAC_KEY` (32+ символов) модуль сам переходит в эффективный `off`
(`disabled_reason=hmac_key_missing`) и пишет ERROR при старте; api и остальные воркеры стартуют
как обычно. Раньше такой `.env` ронял весь api и все воркеры (`validate_runtime_secrets`).

## Права

| Кто | Что может |
| --- | --- |
| Сотрудник (JWT) | загружать и смотреть **свои** скрины, выбирать исход, пока нет вердикта, свою сводку, коды сопряжения и свои установки расширения; чужой скрин для него — 404 |
| Расширение (`mas_…`) | то же от имени сотрудника, к которому привязана установка. Снимает только вкладки с адресов из `allowed_url_prefixes`; сервер такой скрин не отклоняет, а отправляет на проверку (`url_not_chat`), и только если URL прислан — поддельный клиент может прислать любой чат-URL, это ловят правила уникальности |
| Администратор (`CurrentAdmin`) | очереди, карточки целиком (поля, совпадения, оригинал), решения, пересчёт, стирание файла, сводки по менеджерам и экспорт, экран «Конвейер», привязки Telegram |

Менеджер вердикты не меняет. Пороги, совпадения и чьи скрины совпали видит только админ.

## Хранение

Скриншоты лежат в S3 Cloud.ru. Модуль сам в S3 не пишет: запись и удаление — только событиями
в Kafka, их выполняют консьюмеры воркера; в событиях нет байтов. До выгрузки файл лежит в томе
`screenshots_staging` (`/data/screenshots-staging`, общий у api и воркера). Состояние каждого
объекта — таблица `storage_objects` (`staged → uploading → stored → delete_requested → deleted`,
любое → `failed`). Чтение — presigned GET напрямую из S3 на 5 минут: оригинал как вложение,
миниатюра inline.

Ключи по содержимому: `dbs-screenshots/orig/{sha[0:2]}/{sha256}.{ext}`,
`dbs-screenshots/thumb/{sha[0:2]}/{sha256}.jpg`.

| Что | Срок | Как исполняется |
| --- | --- | --- |
| Оригинал | 365 дней от последнего скрина с файлом | `purge_expired`: `delete_requested` и событие удаления; только с S3; оригинал без вердикта или на проверке и закреплённые файлы ждут |
| Миниатюра | 365 дней | так же |
| Тексты: `submissions.text_norm`, MinHash, `caption_raw`; в `extractions` — текст отзыва, реплики, `vlm_json`, `ocr_json` | 3 года (`retention_fields_days` = 1095) | `purge_texts`: обнуляет, у распознавания — когда последний скрин файла старше срока; работает и без S3; повторный запуск ничего не делает |
| Вердикты, исходы, журнал, ключи кейса (`text_key`, `chat_id_norm`, `key_time`), длина текста, HMAC имени, звёзды, флаги | бессрочно | не чистятся: на них KPI прошлых периодов и разбор споров |

Срок текстов обязан быть длиннее окна дедупа (`retention_fields_days > dedupe_window_days`,
проверяется при загрузке настроек): тексты — ключ кандидатов, и стирать их можно только у скринов,
которые кандидатами уже не бывают. По умолчанию 1095 против 90 дней.

Имя покупателя в открытом виде не хранится: только HMAC (`SCREENSHOT_CONTROL_HMAC_KEY`).

Админ стирает файл, пока идёт его выгрузка (`uploading`): объект переходит только в
`delete_requested`, а не сразу в `deleted`. Если delete-подписчик успел «удалить» ещё не
записанный ключ, upload-подписчик после `put` перечитывает строку под блокировкой, видит стирание и
удаляет объект сразу (не вышло — снова `delete_requested` с событием удаления). Миниатюру стёртого
файла распознавание не заводит.

### Без S3

S3 выключен (`S3_ENABLED=false`) или бакет не задан — приём и конвейер работают, файлы копятся
в staging, события выгрузки не публикуются, подписчики хранилища в воркере не стартуют. Ссылки на
картинки не выдаются: `thumb_url=null`, `image-url` отвечает `available=false`; удаление файла
админом стирает staging сразу; чистка файлов по сроку не запускается (тексты чистятся). S3 для
`shadow` не обязателен: бакет можно завести позже, когда S3 появится, часовая сверка выгрузит
накопленное.

У staging два предела, приём отвечает 503 `storage_full` при любом из них:

- **сам каталог** больше `staging_max_bytes` (2 ГБ). Размер считается обходом каталога не чаще
  раза в 30 с на процесс, между обходами к нему прибавляется записанное; проверка идёт в потоке,
  не в event loop. Это главный предел: том общий с PostgreSQL, и без него staging без S3 рос бы,
  пока не съест место базы;
- **том** занят больше `staging_max_used_percent` (85 %) — страховка, если место съело что-то другое.

Скрин — это оригинал (~0,3–2 МБ) и миниатюра; 2 ГБ хватает примерно на 2–5 тыс. скринов. Экран
«Конвейер» показывает в «Временное хранилище» большее из «каталог / 2 ГБ» и «занято на томе»; без
S3 возраст старейшего невыгруженного файла не показывается (файлы ждут S3 по замыслу, это не сбой).

### Расширение (`Authorization: Bearer mas_…`, `X-Extension-Version`)

`POST /pair` (без токена, код из 8 символов Crockford) → `{token, username, min_version,
allowed_url_prefixes}`; код гасится атомарно, повтор — 404 `code_invalid`. Тот же `install_id`
отзывает прежнюю установку; живых установок у сотрудника не больше `max_extension_installs` (3),
лишние старые отзываются. Токен — `mas_` + 32 байта, в базе только sha256.

На каждом запросе: установка не отозвана (401 `install_revoked`), простой не дольше
`extension_token_idle_days` (иначе тоже 401 `install_revoked`), сотрудник активен (403
`user_blocked` сразу после блокировки), версия не ниже `extension_min_version` (426
`upgrade_required`). Ручки: `GET /me`, `POST /submissions` (исход обязателен — 422

`client_meta`), `GET /submissions`, `GET /submissions/{id}`, `GET /summary`.

### Лимиты

- На IP: общий лимитер проекта (`RATE_LIMIT_REQUESTS`, 30/мин на проде) душил бы офис за одним
  адресом, поэтому `…/submissions*` и `…/extension/*` идут по своему бюджету
  `screenshot_control.ip_requests_per_minute` (300/мин, ключи `rate_limit:ip-screenshots`).
  Совсем лимит не снят: multipart читается до авторизации.
- `POST …/extension/pair` — под общим лимитом и под жёстким своим: `pair_attempts_per_window` за
  `pair_window_seconds` с IP (10 за 10 мин), 429 с `Retry-After`.
- На сотрудника (веб и расширение вместе, ключи `sc:user:*`): загрузки `uploads_per_minute` (20) и
  `uploads_per_hour` (120), опрос (списки, карточки, сводка, ссылки) `status_polls_per_minute`
  (120), коды сопряжения — как попытки обмена. 429 `rate_limited` с `Retry-After`.
- Файл: до 15 МБ (`max_upload_bytes`), PNG/JPEG/WEBP по сигнатуре, сторона не меньше 500 px, не
  больше 25 Мп (`max_image_pixels`; реальные скрины до 6K — около 20 Мп). Размер проверяется по
  заголовку до декодирования; полное декодирование — одно за раз на процесс api (25 Мп RGBA —
  ~100 МБ при `mem_limit 512m`), параллельные приёмы ждут своей очереди в потоках.
- Недоступный Redis — 503 `limiter_unavailable`, как у общего лимитера (fail-closed).

## Раскатка

Шаги владельца (на сервере, в `.env`, затем деплой):

1. Бакет и сервисный ключ в Cloud.ru Object Storage (лучше отдельный бакет под ПДн, с
   lifecycle-правилом «срок + 1 день» как страховкой, если Cloud.ru его поддерживает — не
   проверено); `S3_*`, `S3_ENABLED=true`, при отдельном бакете `SCREENSHOT_CONTROL_S3_BUCKET`.
   Включение S3 запустит и существующие подписчики выгрузки отзывов — это безвредно, но стоит
   посмотреть логи. Без S3 модуль работает (см. «Без S3»).
2. Ключ Foundation Models с квотой на распознавание: запрос — порядка 1,5–2 тыс. токенов
   (картинка ужимается сервисом примерно до 1 тыс., этап 0, плюс промпт и ответ); скрин окна
   браузера — два запроса, телефона или из расширения — один, ремонтный запрос — изредка ещё
   один. Точную цифру даст `screenshot_eval` (раздел «Оценка»). `FOUNDATION_MODELS_API_KEY`, при
   желании `VISION_MODEL`.
3. `SCREENSHOT_CONTROL_HMAC_KEY` — случайные 32+ символов (`openssl rand -hex 32`), один раз и
   навсегда.
4. `SCREENSHOT_CONTROL_MODE=shadow`, деплой. Миграция `wb_screenshot_control` идёт в общем
   `migrate`; новый сервис `wb-screenshot-control-worker` — ровно одна реплика. Раздать
   менеджерам расширение (`/extension/marketplace-auto-screenshots.zip`, см.
   [extension/README.md](../../extension/README.md)).
5. Пара недель shadow (S3 для этого не обязателен — staging держит до 2 ГБ, см. «Без S3»):
   разметить выборку и прогнать `screenshot_eval` (ниже), откалибровать
   пороги, разобрать очередь проверки. Затем `SCREENSHOT_CONTROL_KPI_FROM=<дата>` и
   `SCREENSHOT_CONTROL_MODE=enforce`.

Откат — `SCREENSHOT_CONTROL_MODE=off`: приём закрыт, данные и файлы остаются.

### Чек-лист выкладки

- [ ] Миграции до `sc003` применились (`migrate`); `sc003` заполняет `text_minhash` у уже
      распознанных скринов — на пустой базе мгновенно.
- [ ] В логах api и воркера скринов нет ERROR `screenshot_control_disabled` (иначе модуль выключен:
      нет или короткий `SCREENSHOT_CONTROL_HMAC_KEY`) и WARNING `screenshot_control_model_key_missing`
      (нет ключа модели).
- [ ] `wb-screenshot-control-worker` — ровно одна реплика, heartbeat свежий.
- [ ] Экран «Конвейер»: «Временное хранилище» далеко от 85 %. Без S3 оно растёт до 2 ГБ
      (`staging_max_bytes`), потом приём отвечает 503 `storage_full` — до этого завести бакет.
- [ ] В логах воркера нет `screenshot_event_parked`: каждое такое событие — скрин, ушедший на проверку
      из-за ошибки конвейера, и повод разобрать причину.
- [ ] `S3_*` заданы — тогда раз в сутки чистятся и файлы; тексты по сроку чистятся в любом случае.
- [ ] Перед `enforce`: калибровка порогов (`screenshot_eval`), проверка, сколько пар реальных скринов
      совпадает по dHash ≤ 12, и решение по снимку KPI закрытого периода (см. «Не сделано»).

## Не сделано

- **Снимок KPI закрытого периода.** KPI считается по текущему `verdict`: решение админа или
  пересчёт меняют прошлые месяцы задним числом. Нужна таблица снимков (период, менеджер, счётчики,
  кто и когда закрыл) и выгрузка из неё; до этого цифры прошлого периода могут меняться.
- **Генерация TS-типов фронта из OpenAPI.** Схема экспортируется (`just openapi`), но
  `frontend/src/features/screenshotControl/types.ts` пишется руками; в `ErrorCode` фронта нет
  `transition_not_allowed` и `bad_cursor`.
- **Проверка dHash на реальных скринах.** Все скрины кабинета похожи; сколько несвязанных пар даёт
  dHash ≤ 12 на реальных данных, не измерено. Подбор кандидатов от этого больше не теряет дубли
  (у dHash свой лимит). `near_image_conflict` на вердикт не влияет (одинаковый интерфейс даёт
  близкий хеш у разных отзывов); посчитать на shadow-выборке (`SELECT count(*)` пар с
  `bit_count(dhash # x) <= 12`) и решить, нужен ли он как правило.
- Не исправлено из ревью реализации (мелочи): exact-копия своего же файла с другим исходом на
  приёме даёт `duplicate`, а не `caption_conflict`; зависимые дубли отклонённого корня не
  пересчитываются; короткие таймауты boto для delete; `last_seen_at` установки пишется на каждый
  запрос; мёртвая колонка `files.tile_hashes`; `mode` по умолчанию `shadow` в коде и docker-конфиге
  (в compose — `off`).

## Оценка

`backend/commands/screenshot_eval.py` прогоняет настоящий `Extractor` (живая модель Cloud.ru,
ключ из окружения) по папке размеченных скринов и настоящий `decide` по ним же на кандидатах в
памяти:

