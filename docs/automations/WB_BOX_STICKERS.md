# Стикеры коробов FBO

## Зачем

На FBO-поставку склад создаёт короба в кабинете WB, заполняет Excel коробовки (какой
баркод в каком коробе и сколько), загружает его и скачивает PDF со стикерами коробов. На
стикере теперь напечатано количество товара, поэтому стикер должен попасть строго на свой
короб. А WB отдаёт и строки Excel, и страницы PDF в своём порядке, не в том, в котором
стоят упакованные коробки. На поставке в 126 коробов сверять вручную каждый стикер — долго,
и легко ошибиться.

Инструмент переставляет страницы PDF в порядок строк Excel коробовки. На сами стикеры
ничего не допечатывается (решение 25.09.2026): номер по порядку и содержимое короба видны
в таблице на странице, а стикер остаётся ровно тем, что выдал WB.

Это не автоматизация по расписанию: своей базы, воркера и подключения селлеров нет.
Файлы пришли — PDF ушёл.

С 13.10.2026 на той же странице есть шаг раньше: **коробовка из таблицы сборки**. Склад
заполнял шаблон коробовки WB руками, переписывая баркоды и количество из Google-таблицы
сборки строка за строкой; теперь строки вставляются как есть, а шаблон заполняется сам
(см. [Коробовка из таблицы сборки](#коробовка-из-таблицы-сборки)).

## Как сопоставляем

У короба три имени:

| Где | Что | Пример |
| --- | --- | --- |
| текст стикера, колонка «ШК короба» в Excel | короткий номер | `618 0474` / `6180474` |
| QR стикера, колонка «ШК короба для печати в стороннем сервисе», `packageCode` в API | полный код | `$Ts;LEK;G0ac;1;Xk56fFQ;TAS` |

1. **Excel** — порядок коробов и полный код каждого. Короб в нескольких строках — несколько
   баркодов в нём.
2. **PDF** — с каждой страницы текстом короткий номер, количество, номер поставки и
   продавец; из QR — полный код. На стикере два QR, оба с одним кодом.
3. **Кабинет** ищется по номеру поставки: `GET supplies-api /api/v1/supplies/{id}` по
   кабинетам со статусом шлюза `verified`/`delivered`, первым — кабинет, чьё имя напечатано
   на стикере.
4. **Содержимое** — `GET supplies-api /api/v1/supplies/{id}/package`: `packageCode`,
   количество и баркоды короба.
5. **Артикул и размер** по баркоду — из каталога `wb_core` (`list_barcode_cards`).

Сборка блокируется при любой из проблем:

- короб есть в Excel, но его стикера нет в PDF, или наоборот;
- номер на стикере не совпадает с кодом в той же строке Excel;
- QR не читается или один короб в PDF дважды;
- в PDF стикеры разных поставок;
- поставка не нашлась ни в одном кабинете;
- количество на стикере не совпадает с WB (значит, стикеры скачаны до правки коробовки);
- в Excel заполнены баркоды и количество, и они расходятся с WB.

## Сборка PDF

Страницы WB не перерисовываются и ничем не дополняются, а переставляются целиком: стикер
и его QR остаются тем, что выдал WB.

Готовый файл читается заново тем же разбором, что и исходный: номер текстом и QR на каждой
странице сверяются с нужным порядком. Если не сошёлся хоть один стикер, файл не отдаётся.

## Коробовка из таблицы сборки

Процесс склада: создать поставку и короба в кабинете WB → скачать шаблон коробовки
(строка на короб: «Баркод товара» пустой, «Кол-во товаров» 0, «ШК короба» и «ШК короба для
печати» уже стоят) → вписать баркоды и количество → загрузить → скачать стикеры. Данные о
коробах есть только в Google-таблице сборки склада: баркод, количество и схема «3-60+1-40»
(три короба по 60 и один на 40). Шаг 1 на странице заполняет шаблон из этих строк.

**Вставка, а не чтение таблицы.** Менеджер выделяет строки поставки в Google-таблице и
вставляет их в поле; доступ к таблице, сервисный аккаунт и её форма нам не нужны. Колонки
на листах таблицы плавают (на «Регионы_26» осенью на одну меньше, чем летом), поэтому
ничего не ищется по номеру колонки, только по содержимому: баркод — 13 цифр, номер поставки
— 8 цифр перед ним, схема — последняя ячейка вида «3-60+1-40», перед которой есть число,
количество — это число («Сборка склад, шт»). Google превращает «1-4» в дату и показывает
«01.04.2026»; такая ячейка читается как «1-4». Строка без номера поставки, когда у
остальных он есть, пропускается: так в таблице записано «не везем».

**Раскладка.** Короба идут по порядку строк и по порядку внутри схемы, первый короб
получает первую строку шаблона. Так порядок строк файла совпадает с таблицей, и стикеры
на шаге 2 лягут по порядку. В файл пишутся только баркод (строкой: числом Excel покажет
`2,05E+12`) и количество; коды коробов и формат не трогаются — на изменённый формат колонки
кабинет отвечает «Не найден ШК короба». Готовый файл перечитывается разбором коробовки и
при расхождении не отдаётся.

Файл не отдаётся, если:

- в строке нет схемы, схема не сходится с количеством, баркод встречается дважды;
- вставлены строки разных поставок или без номера поставки;
- в шаблоне уже заполненные короба, или коробов больше/меньше, чем по схемам (с подсказкой,
  сколько добавить или удалить в кабинете);
- поставка не нашлась ни в одном кабинете;
- баркода нет среди товаров поставки в WB (`GET /api/v1/supplies/{id}/goods`), количество
  по коробам не равно заявленному, или в поставке заявлен товар, которого нет в строках.
  Кабинет через шаблон такое принял бы и молча добавил товар в поставку.

**Память между шагами.** Выданная коробовка хранится под номером поставки в Redis месяц
(`wb_box_stickers:packing:{supply_id}`), и на шаге 2 вместо Excel выбирается поставка из
списка недавних. Своя схема в Postgres ради шести килобайт на несколько часов лишняя;
Redis в стеке с appendonly, а пропавшую запись заменяет загрузка Excel файлом, как раньше.

Не делается: смешанные короба с двумя товарами (схема их не выражает; вторую строку в файл
дописывают руками, код короба инструмент сохранит), срок годности, прямое чтение таблицы.

## API

| Метод | Что |
| --- | --- |
| `POST /api/v1/wb/box-stickers/packing/check` | multipart `template` + поле `assembly` (вставленный текст) → раскладка: кабинет, поставка, короба по порядку, проблемы |
| `POST /api/v1/wb/box-stickers/packing/build` | то же → заполненный шаблон .xlsx и запись под номером поставки; при проблемах 422 |
| `GET /api/v1/wb/box-stickers/packing/recent` | коробовки, заполненные здесь и не истёкшие |
| `POST /api/v1/wb/box-stickers/check` | multipart `stickers` + `workbook` или поле `supply_id` → сопоставление: кабинет, поставка, короба по порядку, проблемы |
| `POST /api/v1/wb/box-stickers/build` | то же → PDF; при проблемах 422 со списком по строке |

Файл больше 20 МБ — 413 (стикеры на 126 коробов весят меньше мегабайта; лимит nginx —
25 МБ). В PDF больше 2000 страниц не собираем.

## Факты про WB, которые здесь важны

- В Excel коробовки WB пишет размер листа `A1`: `openpyxl` в режиме `read_only` без
  `reset_dimensions()` видит одну ячейку.
- На чужую поставку API поставок отвечает 403, так же как на ключ без категории «Поставки».
  Поэтому при поиске кабинета отказ — это ответ «не мой», а итоговая ошибка называет обе
  причины.
- `package` у поставки, где коробовку ещё не загрузили, отдаёт пустой список.

## Где что

- `backend/modules/wb_box_stickers/application/workbook.py` — разбор Excel.
- `.../application/assembly.py` — разбор вставки из таблицы сборки; `.../application/packing.py` —
  раскладка по коробам и запись в шаблон; `.../application/packing_service.py` — сверка с
  товарами поставки и память; `.../infrastructure/redis/store.py` — хранение в Redis.
- `.../application/stickers.py` — разбор PDF (текст + QR), сборка, проверка.
- `.../application/service.py` — сопоставление и все сверки.
- `.../infrastructure/wb/supplies.py` — поставка и упаковка из API поставок.
- `frontend/src/pages/BoxStickersPage.tsx` — страница «Стикеры коробов».
- `backend/tests/wb_box_stickers/test_box_packing.py` — вставка в формах записи живой таблицы и раскладка.
- `backend/tests/wb_box_stickers/test_box_stickers.py` — синтетические файлы в формате WB: репозиторий
  публичный, настоящие стикеры клиентов в него не кладём. Шрифт с кириллицей для них —
  DejaVu Sans Bold из Debian `fonts-dejavu-core` в `backend/tests/fixtures/`, лицензия рядом.
